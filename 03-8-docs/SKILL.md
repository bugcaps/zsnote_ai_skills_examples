# 개발 문서 및 주석 생성

코드의 동작(What)이 아닌 의도(Why)와 제약 사항(Context)을 중심으로 주석 및 문서를 작성합니다.

## 작업 순서

1. 코드를 분석하여 단순 번역이 아닌, '왜 이렇게 작성되었는지' 파악합니다.
2. `references/doc-conventions.md`를 읽고 프로젝트 문서화 규칙을 확인합니다.
3. 대상 언어의 표준 문서화 포맷(JSDoc, Docstring 등)을 준수하여 작성합니다.
4. 아래 체크리스트로 자가 점검한 뒤 결과를 보고합니다.

## 핵심 규약

- **코드를 그대로 번역한 주석(What)은 작성하지 않습니다.** (예: `i++`에 "i를 1 증가"라고 쓰지 않음)
- 비즈니스 로직, 예외 처리의 이유, 마법의 숫자(Magic Number)의 근거를 명시합니다.
- 함수/클래스 문서에는 입력(Parameters)과 반환(Returns)뿐만 아니라, 발생 가능한 예외(Throws/Errors)를 반드시 기재합니다.
- **코드만으로 의도를 알 수 없으면 추측해서 쓰지 않습니다.** 사용자에게 묻거나 `TODO: 근거 확인 필요`로 남깁니다.
- 주석과 문서만 추가합니다. 코드의 로직, 이름, 포맷은 바꾸지 않습니다.
- 중요한 설계 결정이나 우회(Workaround) 로직에는 `NOTE:`, `TODO:`, `WARNING:` 태그를 활용합니다.

## 체크리스트

작성 후 다음을 확인하고, 어긋난 부분이 있다면 수정 후 보고합니다.

- [ ] 코드를 그대로 설명하는 무의미한 주석이 없다
- [ ] 파라미터와 반환값의 타입 및 목적이 명시되었다
- [ ] 예외나 엣지 케이스 처리 이유가 적혀 있다
- [ ] 언어별 표준 포맷(JSDoc, PEP 257 등)에 맞게 작성되었다
- [ ] 근거를 확인하지 못한 "이유"를 지어내지 않았다
- [ ] 주석 외의 코드는 한 글자도 바뀌지 않았다

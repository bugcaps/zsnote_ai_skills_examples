# 레거시 코드 리팩토링

리팩토링의 성공 기준은 "코드가 깔끔해졌다"가 아니라 "수정 전과 같은 테스트가 통과한다"입니다.

## 작업 순서

1. **기준선 확보**: 코드를 고치기 전에 `bash scripts/test_runner.sh`를 실행합니다. 이미 실패하는 상태라면 리팩토링을 시작하지 않고 보고합니다.
2. **규범 확인**: `references/architecture.md`를 읽고 대상 코드가 어떤 원칙을 어기고 있는지 목록으로 만듭니다.
3. **작게 수정**: 원칙 하나를 적용할 때마다 테스트를 실행합니다. 공개 함수의 시그니처와 반환 형태는 유지합니다.
4. **실패 시 대응**: 테스트가 실패하면 방금 한 수정을 고칩니다. 같은 지점에서 3회 연속 실패하면 그 수정을 되돌리고 멈춘 뒤 사용자에게 보고합니다.
5. **결과 보고**: 적용한 원칙, 변경한 파일, 마지막 테스트 실행 결과를 보고합니다.

## 핵심 규약

- **`tests/` 아래의 파일은 수정하지 않습니다.** 테스트를 통과시키려고 테스트를 고치는 것은 리팩토링이 아닙니다.
- 기능 추가, 버그 수정, 동작 변경을 하지 않습니다. 버그를 발견하면 고치지 않고 보고에 적습니다.
- 파일명이나 클래스명을 바꾸면 그것을 참조하는 모든 파일을 함께 수정합니다.
- 필요 이상의 디자인 패턴을 도입하지 않습니다. `references/architecture.md`에 있는 원칙만 적용합니다.

## 체크리스트

- [ ] 수정 전 테스트가 통과하는 것을 확인했다
- [ ] 수정 후 `test_runner.sh`가 종료 코드 0으로 끝났다
- [ ] `tests/` 아래 파일을 수정하지 않았다
- [ ] 공개 함수의 시그니처가 그대로다

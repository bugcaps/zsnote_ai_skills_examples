# 디자인 시스템 및 디자인 토큰 정의

자연어로 쓰인 디자인 규칙을 기계가 읽는 토큰으로 옮깁니다. 값을 만들어내지 않고 **옮기기만** 합니다.

## 작업 순서

1. **문서 분석**: `references/brand_guidelines.txt` 파일 또는 사용자가 제공한 텍스트를 읽고 색상, 타이포그래피, 간격 등의 디자인 규칙을 파악합니다.
2. **토큰 구조화**: 파악한 규칙을 바탕으로 의미론적(Semantic) 이름이 부여된 디자인 토큰을 설계합니다. (예: `primary-color`, `text-base-size`)
3. **포맷 변환**: 사용자가 요청한 포맷(JSON 또는 CSS)으로 토큰을 작성합니다.

## 핵심 규약

- **의미론적 네이밍**: 토큰 이름은 시각적 속성(예: `red`)이 아닌 역할과 의미(예: `error-color`, `primary-button-bg`)를 반영해야 합니다.
- **계층 구조**: Global(원시 값) - Semantic(역할) - Component(특정 UI 요소) 계층을 유지하며 토큰을 정의합니다.
- **불확실성 배제**: 문서에 없는 값은 지어내지 않습니다. 토큰이 필요한데 문서에 없으면 주석으로 `/* 가이드라인에 없음: 확인 필요 */`를 남깁니다.
- **누락 보고**: 반대로 문서에는 있는데 토큰으로 옮기지 못한 규칙(줄 간격, 여백 원칙 등)은 산출물 끝에 목록으로 보고합니다. 조용히 빠뜨리지 않습니다.

## 체크리스트

- [ ] 토큰 이름이 의미론적으로 작성되었는가?
- [ ] 추출된 값이 원본 문서의 규칙을 정확히 따르는가?
- [ ] JSON 또는 CSS 문법에 오류가 없는가?
- [ ] 원본 문서의 규칙 중 옮기지 못한 것을 목록으로 보고했는가?

# 패키지 의존성 충돌 해결

앞 단계의 결과가 다음 단계의 행동을 결정합니다. 순서를 건너뛰지 않습니다.

## 작업 순서

1. **오류 분석**: 오류 메시지에서 충돌이 난 패키지(Target)와 그것을 요구하는 부모 패키지들(Hosts)을 구분합니다. 메시지가 잘렸으면 `npm ls <Target>` 또는 `pip check`로 보완합니다.
2. **버전 조회**: `npm view <Host>@<설치된 버전> peerDependencies` (pip은 `pip index versions`, `pip show`)로 각 Host가 요구하는 Target 버전 범위를 확인합니다. 기억에 의존해 범위를 적지 않습니다.
3. **교집합 탐색**: 모든 Host를 만족하는 Target 버전 범위가 있는지 판정합니다.
4. **해결책 결정**:
   - 교집합이 **있으면** Target을 그 범위로 맞춥니다(직접 의존성이면 버전 수정, 간접 의존성이면 `overrides`/`resolutions`).
   - 교집합이 **없으면** 어느 Host를 올리거나 교체해야 하는지 대안을 제시하고, 적용 전에 사용자에게 확인합니다.
5. **검증**: 변경을 적용했다면 설치 명령을 우회 옵션 없이 다시 실행해 통과하는지 확인합니다.
6. **결과 기록**: `assets/resolution-log.md` 양식을 채워 보고합니다.

## 핵심 규약

- **`--force`, `--legacy-peer-deps`, `--no-deps`를 해결책으로 쓰지 않습니다.** 교집합이 없고 Host도 바꿀 수 없을 때만 마지막 수단으로 언급하며, 어떤 런타임 위험이 남는지 함께 적습니다.
- 사용자 확인 없이 패키지의 메이저 버전을 올리지 않습니다. 올려야 한다면 하위 호환성이 깨질 수 있음을 경고합니다.
- 락 파일(`package-lock.json` 등)을 지우고 다시 설치하는 방법을 먼저 제안하지 않습니다.

## 체크리스트

- [ ] Target과 Hosts를 구분해 적었다
- [ ] 각 Host의 요구 범위를 CLI로 실제 조회했다
- [ ] 교집합 유무를 명시했다
- [ ] 우회 옵션 없이 설치가 통과하는지 확인했다(또는 확인하지 못한 이유를 적었다)
- [ ] `assets/resolution-log.md` 양식으로 보고했다

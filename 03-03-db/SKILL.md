# 데이터베이스 스키마 및 마이그레이션 설계

요구사항에 맞는 안전한 DB 스키마를 설계하고, 프로젝트의 ORM/마이그레이션 툴에 맞는 코드를 생성합니다.

## 작업 순서

1. **현재 스키마 분석**: `prisma/schema.prisma` 또는 `db/migrations/` 등 기존 스키마 구조를 읽어 테이블 명명 규칙과 제약 조건 스타일을 파악합니다.
2. **설계안 제안**: 새롭게 추가할 테이블이나 컬럼의 데이터 타입, 인덱스, 외래 키(Foreign Key) 전략을 제안합니다.
3. **마이그레이션 코드 생성**: 사용자가 설계안에 동의하면, 실제 실행 가능한 마이그레이션 파일(SQL 또는 ORM 코드)을 작성합니다.
4. 아래 체크리스트로 자가 점검한 뒤 결과를 보고합니다.

## 핵심 규약

- **안전성 최우선**: `DROP TABLE`이나 기존 컬럼 삭제 등 파괴적인 변경을 할 때는 반드시 사용자에게 명시적으로 위험성을 경고합니다.
- **포맷 준수**: 마이그레이션 파일명은 프로젝트 컨벤션(예: `YYYYMMDDHHMMSS_description`)을 따릅니다.
- **자동 적용 금지**: 에이전트는 코드를 생성만 하며, 데이터베이스에 직접 마이그레이션을 실행하지 않습니다. `scripts/apply-migration.sh`도 에이전트가 실행하지 않습니다. 사용자가 터미널에서 `bash scripts/apply-migration.sh <마이그레이션 파일> -- <적용 명령>` 형태로 직접 실행하도록 명령어만 안내합니다.

## 체크리스트

작성 후 다음을 확인하고, 하나라도 어긋나면 고친 뒤 보고합니다.

- [ ] 테이블 및 컬럼 이름이 기존 컨벤션과 일치한다.
- [ ] 파괴적 변경(삭제, 타입 변경)이 포함된 경우 경고 문구를 포함했다.
- [ ] 마이그레이션 스크립트를 직접 실행하지 않고 사용자에게 확인을 요청했다.

> **위험·한계**: 이 스킬은 실제 프로덕션 DB의 데이터를 조작하지 않습니다. 생성된 SQL/마이그레이션 코드는 데이터 유실 방지를 위해 반드시 개발자의 검토 후 적용해야 합니다.

# 백엔드 API 엔드포인트 구현

프로젝트의 기존 구조(라우터, 컨트롤러, 서비스, DTO)를 준수하여 새로운 API 엔드포인트를 순차적으로 구현합니다. 한 번에 모든 코드를 쏟아내지 않고 계층별로 나누어 작업합니다.

## 작업 순서

1. **디렉터리 구조 분석**: `src/` 내의 `routes/`, `controllers/`, `services/`, `dto/` 계층 구조를 파악하고, 기존 API 하나를 읽어 네이밍 규칙을 확인합니다.
2. **DTO 및 유효성 검사 정의**: 요청(Request)과 응답(Response)에 대한 DTO(Data Transfer Object)를 먼저 정의합니다.
3. **서비스(Service) 로직 구현**: 비즈니스 로직을 처리하는 서비스 계층을 작성합니다.
4. **컨트롤러(Controller) 및 라우터(Router) 연결**: 클라이언트의 요청을 받아 서비스를 호출하고, `assets/response-template.json`의 표준 응답 포맷에 맞춰 결과를 반환하는 컨트롤러와 라우터를 작성합니다.
5. 아래 체크리스트로 자가 점검한 뒤 결과를 보고합니다.

## 핵심 규약

- **계층 분리**: 컨트롤러에 비즈니스 로직을 섞지 않고 반드시 서비스 계층을 호출합니다.
- **표준 응답 포맷**: 모든 성공 및 에러 응답은 `assets/response-template.json`의 형태를 준수합니다.
- **점진적 작성**: 코드는 계층별로 한 번에 하나씩 생성하며, 한 파일에 모든 코드를 작성하지 않습니다.
- **에러 처리**: 글로벌 에러 핸들러로 예외를 던지도록 작성하며, `try-catch` 안에서 임의의 형태로 에러를 반환하지 않습니다.

## 체크리스트

작성 후 다음을 확인하고, 하나라도 어긋나면 고친 뒤 보고합니다.

- [ ] 라우터, 컨트롤러, 서비스, DTO가 분리되어 작성되었다.
- [ ] 응답 형식이 `assets/response-template.json` 구조와 일치한다.
- [ ] 컨트롤러 내에 비즈니스(DB 접근 등) 로직이 없다.
- [ ] 글로벌 에러 핸들러를 사용하도록 예외 처리가 되었다.

> **위험·한계**: 이 스킬은 API의 뼈대와 계층 구조를 보장하지만, 복잡한 비즈니스 로직의 결함까지 검증할 수는 없습니다. 생성된 로직은 반드시 개발자가 직접 리뷰해야 합니다.
